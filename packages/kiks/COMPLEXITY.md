# Анализ алгоритмической сложности `kiks`

В документе приведена оценка временной сложности публичных методов библиотеки `kiks` и ключевых вспомогательных операций, которые используются в демонстрационном приложении и benchmark-сценариях.

## Обозначения

- `n` — количество редьюсеров, подключённых к `Store`
- `s` — количество подписчиков store
- `m` — количество middleware
- `k` — стоимость первого вычисления конкретного селектора
- `h` — длина истории состояний
- `t` — количество задач в demo-приложении

## Таблица сложностей

| Модуль | Метод / операция | Сложность | Обоснование |
|---|---|---:|---|
| `Store` | `getState()` | `O(1)` | Возвращается текущая ссылка на состояние без обхода структур. |
| `Store` | `dispatch(action)` | `O(n + s)` | Сначала последовательно вызываются все редьюсеры, затем при изменении состояния уведомляются все подписчики. |
| `Store` | `subscribe(listener)` | `O(1)` | Подписчик добавляется в `Set`. |
| `Store` | `unsubscribe()` | `O(1)` | Подписчик удаляется из `Set`. |
| `Store` | `select(selector)` при повторном вызове | `O(1)` | Готовый memoized selector берётся из `WeakMap`, а при неизменной ссылке на состояние возвращается кешированный результат. |
| `Store` | `select(selector)` при первом вызове | `O(k)` | Для нового селектора создаётся memoized-обёртка, после чего выполняется исходная функция селектора. |
| `Store` | `replaceReducer(...)` | `O(n)` | Формируется новый массив редьюсеров на основе переданного значения. |
| `Store` | `undo()` | `O(1)` | История возвращает предыдущее состояние по указателю без полного обхода массива. |
| `Store` | `redo()` | `O(1)` | Переход вперёд меняет только указатель текущего снимка. |
| `Store` | `timeTravel(index)` | `O(1)` | Выполняется прямой переход к снимку по индексу. |
| `Store` | `canUndo()` | `O(1)` | Проверяется текущее положение указателя истории. |
| `Store` | `canRedo()` | `O(1)` | Проверяется текущее положение указателя относительно конца истории. |
| `History` | `record(state)` | `O(1)` амортизированно | Новый снимок добавляется в конец массива, а указатель обновляется без полного пересчёта истории. |
| `History` | `getCurrentIndex()` | `O(1)` | Возвращается текущее числовое значение указателя. |
| `History` | `getSnapshots()` | `O(h)` | Для выдачи наружу создаётся массив снимков истории. |
| `Selector` | `createSelector(selector)` | `O(1)` | Создаётся функция-обёртка с замыканием под кеширование последнего результата. |
| `Middleware` | построение pipeline | `O(m)` | Цепочка собирается один раз через `reduceRight` при создании store. |
| `loggerMiddleware` | обработка одного экшена | `O(1)` | Middleware делает фиксированное число обращений к `console` и не выполняет обходов. |
| `thunkMiddleware` | обработка обычного экшена | `O(1)` | Выполняется одна проверка типа и передача управления дальше по цепочке. |
| `thunkMiddleware` | обработка thunk-функции | `O(1)` без учёта тела thunk | Middleware лишь вызывает функцию с `dispatch` и `getState`; сложность её логики определяется пользовательским кодом. |
| Demo | `getVisibleTasks(state)` | `O(t log t)` | Сначала выполняется линейная фильтрация списка задач, затем сортировка результата. |
| Demo | `getTaskStats(state)` | `O(t)` | Для подсчёта завершённых задач требуется один проход по массиву. |
| Demo | `getRootCategories(state)` | `O(c)` | Формируется новый список корневых категорий через фильтрацию массива категорий. |

## Пояснения к ключевым оценкам

### `dispatch(action)` в `Store`

Метод `dispatch` вызывает внутренний `dispatchPipeline`. В базовом сценарии это приводит к последовательному выполнению всех редьюсеров над текущим состоянием. Поэтому основная часть стоимости равна `O(n)`. Если состояние действительно изменилось, дополнительно вызывается `emit`, который проходит по множеству подписчиков, что добавляет `O(s)`.

Итог: `O(n + s)`.

### Мемоизированные селекторы

При первом обращении `Store.select` ищет селектор в `WeakMap`. Если селектор ещё не кешировался, создаётся memoized-обёртка и вызывается исходная функция селектора. Эта стоимость зависит от самой логики вычисления, поэтому обозначена как `O(k)`.

При повторном вызове с той же ссылкой на состояние возвращается уже сохранённый результат, поэтому трудоёмкость становится `O(1)`.

### История состояний

Модуль `History` хранит timeline в массиве и индекс текущего снимка. Операции `undo`, `redo` и `timeTravel` не пересчитывают всю историю, а только изменяют указатель либо возвращают элемент по индексу, поэтому они имеют константную сложность.

Запись нового состояния через `record` считается `O(1)` амортизированно: добавление в конец массива обычно константно, а редкие перераспределения памяти массива усредняются по серии операций.

### Построение middleware pipeline

Pipeline формируется один раз в конструкторе `Store` с помощью `reduceRight`. Каждый middleware участвует в композиции ровно один раз, поэтому сложность этой стадии — `O(m)`. После инициализации store pipeline повторно не собирается.

## Вывод

Библиотека `kiks` использует простые и предсказуемые структуры данных:

- `Set` для подписчиков даёт `O(1)` на подписку и отписку;
- `WeakMap` обеспечивает `O(1)` доступ к кешу селекторов и предотвращает удержание неиспользуемых ключей;
- массив history с индексом делает `undo`, `redo` и `timeTravel` константными;
- композиция middleware имеет линейную стоимость только на этапе создания store.

Такой профиль сложности хорошо подходит для дипломного обоснования: основные пользовательские операции имеют либо константную, либо линейную сложность, а более дорогие вычисления сосредоточены в явно контролируемых местах, например в пользовательских селекторах и сортировке demo-списка задач.

## Стратегии `Selector`

Для модуля `Selector` в ядре теперь поддерживаются четыре стратегии, которые можно сравнивать отдельно:

| Стратегия | Повторный вызов | Несвязанное изменение state | Память | Идея |
|---|---:|---:|---:|---|
| `full-recompute` | `O(k)` | `O(k)` | `O(1)` | Всегда выполняет полный пересчёт projector-функции |
| `last-result` | `O(1)` при совпадении ключа | `O(1)` при неизменном cache key | `O(1)` | Держит последний результат и один составной cache key |
| `state-reference` | `O(1)` при той же ссылке на state | `O(k)` при новом объекте state | `O(1)` | Переиспользует значение только при идентичной ссылке на состояние |
| `dependencies` | `O(d)` на проверку зависимостей, затем `O(1)` при cache hit | `O(d)` | `O(d)` | Сравнивает только явные входные срезы состояния |

Обозначения:

- `k` — стоимость самого вычисления selector;
- `d` — число явно указанных зависимостей selector.

В практической части победившей стратегией считается `dependencies`, так как она лучше остальных переживает несвязанные изменения состояния и помогает сохранять стабильный snapshot для `useSyncExternalStore`.
