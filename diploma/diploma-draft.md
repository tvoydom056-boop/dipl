# Разработка библиотеки управления состоянием для React-приложений

## Введение

### Актуальность темы

Современная разработка пользовательских интерфейсов характеризуется высокой динамичностью, ростом сложности клиентской логики и увеличением требований к производительности. В экосистеме React управление состоянием является одной из центральных задач, так как именно состояние определяет отображение компонентов, координацию пользовательских действий, обработку асинхронных операций и синхронизацию интерфейса с бизнес-логикой приложения.

На практике для решения этой задачи применяются как встроенные возможности React, так и специализированные библиотеки управления состоянием. Однако существующие решения не всегда одновременно обеспечивают минимальный размер пакета, встроенную поддержку истории состояний, строгую типизацию, простоту использования и отсутствие внешних зависимостей. Для учебных, исследовательских и некоторых production-сценариев актуальной становится разработка собственной библиотеки, ориентированной на баланс между архитектурной строгостью, компактностью и расширяемостью.

Дополнительную актуальность теме придаёт рост требований к наблюдаемости состояния приложения. В условиях отладки сложных интерфейсов особое значение приобретают возможности просмотра истории изменений и перехода по временной шкале состояний. В большинстве существующих решений подобный функционал либо выносится во внешние инструменты, либо требует дополнительных пакетов. Это усложняет внедрение и снижает автономность библиотеки.

В связи с этим разработка специализированной библиотеки управления состоянием для React-приложений, обеспечивающей встроенный time-travel, строгую типизацию, middleware-механизм, селекторы и минималистичную архитектуру, представляет собой актуальную научно-практическую задачу.

### Цель работы

Целью магистерской диссертации является разработка библиотеки управления состоянием для React-приложений под названием `kiks`, ориентированной на production-ready использование, а также проведение её сравнительного анализа с распространёнными решениями экосистемы React.

### Задачи работы

Для достижения поставленной цели в работе решаются следующие задачи:

1. Проанализировать существующие подходы к управлению состоянием в React-приложениях.
2. Исследовать архитектурные особенности библиотек Redux Toolkit, Zustand и MobX.
3. Сформулировать требования к разрабатываемой библиотеке `kiks`.
4. Спроектировать архитектуру библиотеки с учётом требований нулевых внешних зависимостей, встроенного time-travel и строгой типизации.
5. Реализовать ядро библиотеки, включающее `Store`, `Action`, `Reducer`, `History`, `Selector`, middleware и React-интеграцию.
6. Разработать тестовое приложение, реализованное идентично на `kiks`, Redux Toolkit, Zustand и MobX.
7. Выполнить сравнительный анализ решений по набору критериев: производительность, размер сборки, выразительность API и встроенные возможности.
8. Сформулировать выводы о применимости и эффективности разработанной библиотеки.

### Объект и предмет исследования

Объектом исследования являются механизмы управления состоянием в клиентских веб-приложениях, разработанных с использованием React.

Предметом исследования являются архитектурные, типовые, производительные и эксплуатационные характеристики библиотеки управления состоянием для React-приложений.

### Научная новизна

Научная новизна работы состоит в следующем:

1. Предложена архитектура лёгкой библиотеки управления состоянием для React, объединяющая ООП-подход, встроенную историю состояний и минималистичное API.
2. Реализован механизм встроенного time-travel без использования внешних DevTools-расширений.
3. Предложен подход к встроенной мемоизации селекторов без подключения сторонних библиотек.
4. Разработана библиотека, сочетающая строгую типизацию TypeScript, middleware-механизм и React-интеграцию при отсутствии runtime-зависимостей, кроме React как `peerDependency`.

### Практическая значимость

Практическая значимость работы заключается в создании библиотеки `kiks`, пригодной для использования в учебных и прикладных React-проектах, а также в подготовке демонстрационного стенда, позволяющего сравнивать различные подходы к управлению состоянием в одинаковом предметном сценарии.

## Глава 1. Теоретические основы управления состоянием в React-приложениях

### 1.1. Понятие состояния в клиентском приложении

В контексте интерфейсной разработки состояние представляет собой совокупность данных, от которых зависит текущее отображение приложения. К состоянию относятся пользовательский ввод, данные с сервера, локальные флаги, параметры фильтрации, история взаимодействия и производные значения, вычисляемые на основе исходных структур.

В React состояние напрямую влияет на процесс повторного рендеринга компонентов. Неправильная организация state management ведёт к ряду проблем:

1. избыточным повторным рендерам;
2. затруднённой отладке;
3. повышенному количеству шаблонного кода;
4. дублированию логики обновления состояния;
5. сложности сопровождения крупных приложений.

Следовательно, система управления состоянием должна обеспечивать предсказуемое обновление данных, удобную подписку компонентов, расширяемость и воспроизводимость поведения приложения.

### 1.2. Подходы к управлению состоянием в React

В экосистеме React можно выделить несколько основных подходов к организации состояния:

1. Локальное состояние компонентов. Реализуется через `useState`, `useReducer` и другие хуки React. Подходит для небольших и изолированных сценариев, но плохо масштабируется при сложном обмене данными.
2. Контекстный подход. React Context позволяет передавать состояние через дерево компонентов, однако сам по себе не предоставляет развитых механизмов оптимизации, истории изменений или middleware.
3. Централизованное хранилище. Данные приложения сосредоточены в одном или нескольких store-объектах, а компоненты подписываются на нужные фрагменты состояния.
4. Реактивный подход. Изменения в моделях автоматически распространяются на зависимые представления. Данный подход характерен, например, для MobX.

Каждый из подходов имеет преимущества и ограничения, поэтому выбор зависит от целей проекта, требований к производительности, удобству тестирования и сопровождения.

### 1.3. Анализ существующих решений

#### 1.3.1. Redux Toolkit

Redux Toolkit является современным стандартом экосистемы Redux. Библиотека предоставляет централизованный store, декларативное описание reducer-логики и развитую инфраструктуру для асинхронных операций.

Преимущества Redux Toolkit:

1. предсказуемость архитектуры;
2. развитая экосистема;
3. удобная интеграция с DevTools;
4. стандартизированный подход к организации проекта.

Недостатки Redux Toolkit:

1. сравнительно высокий объём инфраструктурного кода;
2. зависимость от дополнительного инструментария для удобного time-travel;
3. достаточно крупный вес экосистемы относительно минималистичных решений.

#### 1.3.2. Zustand

Zustand ориентирован на минимализм и простоту. Он предоставляет компактный API, близкий к React hooks-подходу, и часто используется как лёгкая альтернатива Redux.

Преимущества Zustand:

1. низкий порог входа;
2. минимальный шаблонный код;
3. небольшая концептуальная сложность.

Недостатки Zustand:

1. менее жёстко формализованная архитектура;
2. отсутствие встроенного time-travel как базовой возможности;
3. необходимость самостоятельного проектирования расширенных механизмов истории и middleware.

#### 1.3.3. MobX

MobX использует реактивную модель, где изменения observable-объектов автоматически приводят к обновлению зависящих компонентов.

Преимущества MobX:

1. высокая выразительность реактивной модели;
2. относительно небольшое количество шаблонного кода;
3. удобство описания изменяемых доменных моделей.

Недостатки MobX:

1. менее очевидная трассировка изменений по сравнению с reducer-подходом;
2. необходимость глубокого понимания реактивной модели;
3. дополнительные усилия при воспроизводимом сравнительном анализе и формализации истории состояний.

### 1.4. Обоснование разработки собственной библиотеки

Анализ существующих решений показывает, что каждое из них решает задачу управления состоянием с собственной стороны:

1. Redux Toolkit делает акцент на предсказуемости и инфраструктуре.
2. Zustand ориентирован на лаконичность.
3. MobX удобен для реактивного программирования.

Однако в рамках поставленной задачи требовалась библиотека, одновременно обладающая следующими свойствами:

1. отсутствием внешних runtime-зависимостей;
2. встроенной поддержкой time-travel;
3. строгой типизацией на TypeScript;
4. встроенными селекторами;
5. middleware-системой;
6. минималистичной архитектурой, пригодной для учебного и исследовательского анализа.

Именно сочетание этих требований обусловило необходимость разработки собственной библиотеки `kiks`.

## Глава 2. Проектирование библиотеки kiks

### 2.1. Требования к библиотеке

В результате анализа были сформулированы следующие функциональные и нефункциональные требования к библиотеке:

1. библиотека должна иметь нулевые внешние runtime-зависимости;
2. React должен подключаться как `peerDependency`;
3. библиотека должна поддерживать централизованный store;
4. библиотека должна иметь встроенную историю состояний;
5. библиотека должна обеспечивать строгую типизацию состояния и экшенов;
6. библиотека должна предоставлять мемоизированные селекторы;
7. библиотека должна поддерживать middleware;
8. библиотека должна интегрироваться с React через хук и провайдер;
9. библиотека должна быть пригодна для unit-тестирования и сравнительных замеров.

### 2.2. Архитектурная концепция

Архитектура `kiks` основана на ООП-подходе и включает несколько функционально изолированных слоёв:

1. Ядро хранения состояния.
2. Механизм истории состояний.
3. Подсистема селекторов.
4. Middleware-слой.
5. React-интеграция.

Базовой сущностью библиотеки выступает класс `Store<TState, TAction>`, который инкапсулирует текущее состояние, набор reducer-обработчиков, подписчиков и историю изменений.

Архитектура спроектирована так, чтобы ключевые модули были слабо связаны между собой:

1. `Action` отвечает только за представление действия.
2. `Reducer` описывает преобразование состояния.
3. `Store` координирует применение reducer-цепочки и уведомление подписчиков.
4. `History` инкапсулирует timeline состояний.
5. `Selector` выполняет мемоизацию вычисляемых значений.
6. middleware расширяет процесс `dispatch`, не изменяя внутреннюю модель состояния.

### 2.3. Ключевые модули

#### 2.3.1. Action

Класс `Action<TType, TPayload>` представляет отдельное действие, инициирующее изменение состояния. Он содержит тип действия и полезную нагрузку.

Использование generics позволяет типизировать как строковый идентификатор действия, так и структуру payload, что особенно важно для TypeScript-проектов.

#### 2.3.2. Reducer

Абстрактный класс `Reducer<TState, TAction>` задаёт контракт преобразования состояния. Каждый конкретный reducer реализует метод `reduce(state, action): state`.

Такой подход даёт следующие преимущества:

1. явное разделение логики состояния;
2. удобство расширения и тестирования;
3. читаемость кода, пригодного для цитирования в дипломной работе.

#### 2.3.3. Store

Класс `Store` является центром библиотеки. Он реализует:

1. хранение текущего состояния;
2. диспетчеризацию действий через `dispatch`;
3. подписку и отписку слушателей;
4. замену reducer-логики;
5. интеграцию с историей состояний и селекторами;
6. применение middleware.

#### 2.3.4. History

Модуль `History` хранит временную шкалу состояний и указатель на текущий элемент timeline. Он предоставляет следующие методы:

1. `record(state)`;
2. `undo()`;
3. `redo()`;
4. `timeTravel(index)`;
5. `getSnapshots()`;
6. `getCurrentIndex()`.

Таким образом, библиотека получает встроенную поддержку time-travel без необходимости внешних DevTools.

#### 2.3.5. Selector

Модуль `Selector` реализует мемоизацию производных вычислений. Базовая идея заключается в кешировании результата по ссылке на объект состояния. Если ссылка на state не изменилась, повторное вычисление не выполняется.

Это позволяет сократить количество лишних операций при чтении производных данных и отказаться от использования сторонних решений наподобие `reselect`.

#### 2.3.6. Middleware

Middleware в `kiks` реализован как цепочка функций, оборачивающих базовый `dispatch`. В библиотеку включены:

1. `loggerMiddleware()` для логирования переходов;
2. `thunkMiddleware()` для обработки асинхронных функций.

Подобный механизм делает библиотеку расширяемой без изменения кода ядра.

#### 2.3.7. React-интеграция

Для интеграции с React реализованы:

1. `Provider` для передачи store через Context;
2. `useKiks` для подписки компонентов на store.

Хук построен на `useSyncExternalStore`, что соответствует современному рекомендуемому способу интеграции внешних хранилищ с React.

### 2.4. Публичный API библиотеки

На текущем этапе библиотека экспортирует:

1. `Action`;
2. `Reducer`;
3. `Store`;
4. `History`;
5. `createSelector`;
6. `Provider`;
7. `useKiks`;
8. `loggerMiddleware`;
9. `thunkMiddleware`.

Также доступны типы `StoreOptions`, `Selector`, `MemoizedSelector`, `Middleware`, `ThunkAction` и другие вспомогательные интерфейсы.

### 2.5. Проектные решения

В рамках проектирования были приняты следующие ключевые решения:

1. использовать TypeScript `strict mode`;
2. избегать `any` в публичном API;
3. выносить каждый модуль в отдельный файл;
4. сохранять комментарии на русском языке;
5. закладывать расширяемость для дальнейшей сборки и публикации npm-пакета.

## Глава 3. Реализация библиотеки kiks

### 3.1. Структура проекта

Проект организован в монорепозиторной структуре и включает два основных блока:

1. `packages/kiks` — библиотека `kiks`;
2. `demo` — демонстрационное приложение и benchmark-стенд.

Структура пакета `kiks` включает директории `core`, `middleware`, `react`, `tests`.

### 3.2. Реализация ядра

Ядро библиотеки реализовано в файлах:

1. `Action.ts`;
2. `Reducer.ts`;
3. `Store.ts`.

В классе `Store` реализована последовательная обработка действий через цепочку reducer-объектов. После вычисления нового состояния производится сравнение ссылок через `Object.is`. Если состояние не изменилось, подписчики не уведомляются. Это позволяет исключить лишние обновления.

Подписка реализована через множество `Set<Listener<TState>>`, что обеспечивает:

1. уникальность обработчиков;
2. простую отписку;
3. предсказуемую сложность обхода слушателей.

### 3.3. Реализация истории состояний

Модуль `History` хранит внутренний массив состояний `timeline` и индекс текущего состояния `pointer`. При каждом изменении состояния store записывает новый snapshot в историю.

Ключевые особенности реализации:

1. если после `undo()` происходит новый `dispatch()`, будущая ветка истории обрезается;
2. поддерживается ограничение длины истории через `historyLimit`;
3. переход к произвольному snapshot выполняется методом `timeTravel(index)`.

Это делает библиотеку удобной для отладки и анализа пользовательских сценариев.

### 3.4. Реализация селекторов

Селекторы реализованы в модуле `Selector.ts`. Для мемоизации используется сравнение по ссылке на состояние. Внутри `Store` применён `WeakMap`, в котором кешируются memoized-версии селекторных функций.

Такой подход обеспечивает:

1. повторное использование селекторов;
2. отсутствие внешних зависимостей;
3. сокращение вычислительных затрат при повторном чтении одного и того же производного значения.

### 3.5. Реализация middleware

Middleware-инфраструктура реализована как композиция функций вида:

`MiddlewareApi -> next -> action`.

В библиотеку включены:

1. `loggerMiddleware`, выводящий в консоль тип действия и состояние до и после применения;
2. `thunkMiddleware`, позволяющий передавать в `dispatch` функцию с доступом к `dispatch` и `getState`.

Такой механизм даёт возможность расширять поведение store без модификации базового алгоритма изменения состояния.

### 3.6. React-интеграция

Хук `useKiks` поддерживает несколько вариантов использования:

1. `useKiks(store)`;
2. `useKiks(store, selector)`;
3. `useKiks(selector)` при наличии `Provider`.

Использование `useSyncExternalStore` обеспечивает корректную подписку на внешний store и совместимость с актуальной моделью React.

### 3.7. Тестирование

Для библиотеки были реализованы unit-тесты на базе Vitest. Проверены следующие сценарии:

1. изменение состояния через `dispatch`;
2. работа подписчиков;
3. отсутствие уведомления при неизменном состоянии;
4. замена reducer-логики;
5. корректность `undo`, `redo`, `timeTravel`;
6. ограничение длины истории;
7. мемоизация селекторов.

По итогам тестирования все 11 тестов завершились успешно.

### 3.8. Реализация демонстрационного приложения

Для сравнительного анализа разработано тестовое приложение “Менеджер задач”. Оно реализовано идентично на четырёх решениях:

1. `kiks`;
2. Redux Toolkit;
3. Zustand;
4. MobX.

Функциональность приложения включает:

1. CRUD-операции над задачами;
2. поиск;
3. фильтрацию;
4. сортировку;
5. иерархию категорий;
6. счётчик операций;
7. панель time-travel.

Общий пользовательский интерфейс вынесен в единый компонент, а различия реализованы на уровне адаптеров состояния. Это обеспечивает корректность сравнительного анализа.

## Глава 4. Сравнительный анализ

### 4.1. Методика исследования

Сравнительный анализ выполнялся по следующим критериям:

1. `dispatch ops/sec`;
2. размер production bundle;
3. количество ре-рендеров;
4. объём шаблонного кода;
5. наличие встроенных возможностей.

Для обеспечения сопоставимости результатов использовались идентичные сценарии данных и одинаковая UI-обвязка тестового приложения.

### 4.2. Результаты dispatch benchmark

Замер dispatch-производительности проводился на 100000 последовательных операций изменения состояния.

Результаты представлены в таблице 4.1.

| Библиотека | ops/sec | Время, ms |
|---|---:|---:|
| kiks | 376815.31 | 265.38 |

| MobX | 3838.88 | 26049.26 |
| Redux Toolkit | 1647.88 | 60684.07 |

Из полученных результатов видно, что разработанная библиотека `kiks` показала наивысшую скорость последовательной диспетчеризации в рамках реализованного сценария. Это объясняется компактностью внутренней модели, отсутствием дополнительной инфраструктуры и прямой reducer-обработкой без тяжёлых промежуточных слоёв.

Следует учитывать, что конкретные значения зависят от характера теста и реализации benchmark-сценария. Тем не менее в рамках одинаковых условий измерения `kiks` продемонстрировала лучшие показатели.

### 4.3. Результаты bundle benchmark

Измерение размера сборки проводилось по отдельным production entry points demo-приложения.

Результаты представлены в таблице 4.2.

| Библиотека | Raw, kB | Gzip, kB |
|---|---:|---:|
| kiks | 209.64 | 65.87 |

Полученные результаты показывают, что по размеру полного demo-сценария `kiks` занимает промежуточное положение между Zustand и Redux Toolkit, при этом заметно выигрывает у MobX. Следует подчеркнуть, что данные значения относятся к полному демонстрационному приложению, а не к изолированному размеру самой библиотеки `kiks`.

### 4.4. Анализ количества ре-рендеров

Автоматизированный CLI-замер количества ре-рендеров не даёт корректной картины без профилирования в браузерной среде. Поэтому для данного показателя предлагается использовать React DevTools Profiler на одинаковом пользовательском сценарии:

1. добавление задачи;
2. изменение статуса задачи;
3. обновление строки поиска;
4. переход по истории состояний.

Такой подход соответствует принятой практике измерения рендерингового поведения React-приложений.

### 4.5. Анализ шаблонного кода

С качественной точки зрения можно отметить следующее:

1. Redux Toolkit требует наиболее выраженной инфраструктурной обвязки.
2. Zustand и MobX отличаются более компактной прикладной записью.
3. `kiks` занимает промежуточную позицию: архитектура более формализована, чем у Zustand, но при этом остаётся компактной и предсказуемой.

Для `kiks` характерно небольшое число ключевых сущностей:

1. `Action`;
2. `Reducer`;
3. `Store`;
4. `useKiks`.

Это упрощает чтение и сопровождение кода, что особенно важно в учебном и исследовательском контексте.

### 4.6. Сравнение встроенных возможностей

Таблица 4.3 содержит качественное сравнение встроенных возможностей.

| Возможность | kiks | Redux Toolkit | Zustand | MobX |
|---|---|---|---|---|
| Строгая TypeScript-типизация | Да | Да | Да | Да |
| Централизованный store | Да | Да | Да | Условно |
| Встроенный time-travel | Да | Нет | Нет | Нет |
| Встроенные селекторы | Да | Частично | Частично | Нет |
| Middleware из коробки | Да | Да | Частично | Нет |
| Нулевые runtime-зависимости ядра | Да | Нет | Нет | Нет |

Из таблицы видно, что `kiks` выгодно отличается встроенным time-travel, отсутствием runtime-зависимостей и наличием встроенных селекторов.

### 4.7. Выводы по сравнительному анализу

Проведённый анализ показывает, что:

1. `kiks` обеспечивает высокую производительность в рассмотренном benchmark-сценарии;
2. библиотека предлагает встроенный функционал, который в альтернативных решениях чаще требует внешних инструментов;
3. по размеру итоговой demo-сборки `kiks` уступает Zustand, но остаётся компактнее Redux Toolkit и MobX;
4. архитектура `kiks` хорошо подходит для учебного исследования и может выступать основой для дальнейшей оптимизации и публикации.
