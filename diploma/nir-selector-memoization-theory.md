# 1. Теоретические основы выбора механизма мемоизации селекторов в библиотеке `kiks`

## 1.1. Постановка задачи

В современных React-приложениях производные данные редко совпадают с первичным состоянием. Как правило, интерфейс опирается не на «сырые» структуры `state`, а на результаты фильтрации, сортировки, агрегации и композиции нескольких фрагментов состояния. Такие вычисления удобно инкапсулировать в селекторах. Селектором далее будем называть функцию вида

\[
y = f(x),
\]

где `x` — текущее состояние приложения или его часть, а `y` — производное значение, используемое компонентами пользовательского интерфейса.

Если селектор вызывается повторно при каждом рендере, а вычисление `f(x)` имеет нетривиальную стоимость `O(k)`, то при росте числа компонентов и частоты обновлений состояние начинает оказывать прямое влияние на отзывчивость интерфейса. В связи с этим в архитектуре библиотек управления состоянием появляется задача мемоизации: необходимо сохранить результат предыдущего вычисления и переиспользовать его, если входные данные не изменились.

Для библиотеки `kiks` задача мемоизации имеет особое значение по трем причинам.

1. Библиотека ориентирована на минимальный runtime и отсутствие внешних зависимостей.
2. React-интеграция построена на `useSyncExternalStore`, а значит, стабильность снимка состояния и производных значений напрямую влияет на частоту обновлений интерфейса.
3. В ядре `Store` уже используется слабое отображение `WeakMap<Selector, MemoizedSelector>`, что делает вопрос выбора самого механизма мемоизации не только теоретическим, но и архитектурным.

Следовательно, в рамках НИР требуется не просто описать селекторы как вспомогательный механизм, а формально выбрать наиболее подходящий способ их мемоизации. Для этого далее рассматриваются четыре альтернативы:

1. отсутствие мемоизации;
2. LRU-кэш ограниченного размера;
3. мемоизация по ссылке на объект состояния через `WeakMap`;
4. мемоизация с явными зависимостями (`input selectors`).

В конце раздела необходимо решить две взаимосвязанные задачи:

- сравнить четыре варианта как алгоритмы;
- применить четыре формальных метода многокритериального выбора и определить лучший вариант для `kiks`.

**Вывод по подразделу 1.1.**  
Проблема мемоизации селекторов в библиотеке управления состоянием является частным случаем задачи оптимизации повторных вычислений производных данных. Для `kiks` эта задача имеет инженерную и исследовательскую значимость, поскольку выбор способа мемоизации влияет одновременно на производительность, безопасность памяти, простоту интеграции и итоговую архитектуру ядра.

## 1.2. Вариант 1. Отсутствие мемоизации (baseline)

### 1.2.1. Определение и математическая основа

Базовый вариант не использует никакого кеша. Селектор рассматривается как чистая функция

\[
f: X \rightarrow Y,
\]

где каждый вызов `f(x)` приводит к полному повторному вычислению результата независимо от того, совпадает ли текущее состояние с предыдущим.

Если стоимость вычисления селектора обозначить как `O(k)`, то временная сложность не зависит от истории вызовов:

\[
T_{\text{first}} = O(k), \qquad T_{\text{repeat}} = O(k).
\]

### 1.2.2. Алгоритм работы

Алгоритм baseline-подхода предельно прост:

1. принять текущее состояние `x`;
2. выполнить тело селектора `f(x)`;
3. вернуть результат `y`.

Псевдокод:

```text
function select(state):
    return f(state)
```

### 1.2.3. Сложность, память и сборщик мусора

Временная сложность:

- первый вызов: `O(k)`;
- повторный вызов: `O(k)`.

Потребление памяти:

\[
M = O(1),
\]

если не учитывать память на сам результат вычисления.

Поведение сборщика мусора наиболее благоприятно: дополнительных структур кеша не создается, а значит, отсутствуют долгоживущие ссылки на прошлые состояния и результаты.

### 1.2.4. Преимущества и недостатки

Преимущества:

- минимальная реализационная сложность;
- отсутствие накладных расходов на сравнение входов;
- отсутствие риска удержания старых данных кешем.

Недостатки:

- полное повторное вычисление даже при неизменном состоянии;
- высокая стоимость в сценариях частого повторного доступа;
- отсутствие стабилизации ссылок на производные данные, что может провоцировать дополнительные `re-render`.

### 1.2.5. Пример реального использования

Такой подход характерен для библиотек, где встроенный слой мемоизации селекторов отсутствует. В контексте сравниваемых инструментов ближе всего к этому варианту находится `Zustand`: библиотека предоставляет механизм подписки на срезы состояния, но не содержит встроенного универсального слоя мемоизации производных селекторов как части ядра [6].

**Вывод по подразделу 1.2.**  
Baseline-подход является важной точкой отсчета: он прост, безопасен с точки зрения памяти и почти не требует инфраструктуры. Однако при повторных вычислениях он не устраняет основную проблему — повторное выполнение одной и той же функции `f(x)` при неизменном входе.

## 1.3. Вариант 2. LRU-кэш ограниченного размера

### 1.3.1. Определение и математическая основа

LRU (`Least Recently Used`) — это стратегия кеширования, при которой хранятся последние `N` результатов, а при переполнении удаляется наименее недавно использованная запись. Математически такой кеш можно представить как отображение

\[
C: K \rightarrow V,
\]

дополненное отношением порядка по времени последнего доступа.

Классическая реализация использует:

- хэш-таблицу для доступа по ключу за `O(1)`;
- двусвязный список для поддержки порядка «самый новый — самый старый».

### 1.3.2. Алгоритм работы

Пусть `key = h(x)` — ключ, построенный на основе аргумента или набора аргументов селектора.

Псевдокод:

```text
function select(state):
    key = h(state)
    if key in hashTable:
        move key to head of linked list
        return hashTable[key].value
    else:
        value = f(state)
        insert (key, value) to hashTable and list head
        if size(cache) > N:
            evict tail element
        return value
```

При попадании в кеш (`cache hit`) селектор фактически работает за `O(1)`, а при промахе (`cache miss`) общая стоимость равна

\[
T_{\text{miss}} = O(k) + O(1).
\]

### 1.3.3. Сложность, память и сборщик мусора

Временная сложность:

- первый вызов: `O(k)`;
- повторный вызов при попадании в кеш: `O(1)`;
- повторный вызов при промахе: `O(k)`.

Потребление памяти:

\[
M = O(N),
\]

где `N` — размер кеша.

Поведение сборщика мусора менее благоприятно, чем в варианте без мемоизации. Поскольку LRU-кеш хранит сильные ссылки на ключи и значения, объекты состояния и результаты вычислений остаются достижимыми до момента вытеснения. При неудачном выборе `N` это увеличивает риск удержания данных в памяти дольше, чем необходимо.

### 1.3.4. Преимущества и недостатки

Преимущества:

- высокая скорость повторного доступа при хорошем коэффициенте попаданий;
- возможность кешировать несколько последних состояний, а не только одно;
- универсальность для селекторов с разными шаблонами вызовов.

Недостатки:

- дополнительная сложность реализации;
- необходимость выбора параметра `N`;
- сильные ссылки на кешированные элементы;
- риск ухудшения свойств по памяти при длительно живущих селекторах.

### 1.3.5. Пример реального использования

Исторически LRU-подход применялся в старых конфигурациях `Reselect` и по-прежнему доступен как стратегия `lruMemoize` [4], [5]. Такой подход хорошо работает в вычислительных сценариях с повторяющимися наборами аргументов, но хуже согласуется с требованием минимального и безопасного по памяти ядра.

**Вывод по подразделу 1.3.**  
LRU-кеш существенно ускоряет повторные вызовы, однако достигает этого ценой усложнения реализации и удержания сильных ссылок на кешированные объекты. Для компактной библиотеки с zero-dependencies этот вариант полезен как сильная альтернатива, но не как безусловно оптимальный базовый механизм.

## 1.4. Вариант 3. WeakMap-мемоизация по ссылке на `state`

### 1.4.1. Определение и математическая основа

В третьем варианте ключом кеша выступает сам объект состояния. Формально кеш описывается как слабое отображение

\[
W: S \rightharpoonup Y,
\]

где `S` — множество объектов состояния, а `Y` — множество результатов селектора. Отображение является частичным, потому что запись существует только для тех ключей, которые были ранее вычислены и еще не удалены сборщиком мусора.

Если при повторном вызове выполняется условие

\[
state_{curr} \equiv state_{prev},
\]

то есть текущий объект состояния тождественен предыдущему по ссылке, результат может быть возвращен из кеша без повторного вычисления `f(state)`.

### 1.4.2. Алгоритм работы

Псевдокод:

```text
weakCache = WeakMap<object, value>()

function select(state):
    if weakCache.has(state):
        return weakCache.get(state)
    value = f(state)
    weakCache.set(state, value)
    return value
```

Если библиотека дополнительно использует внешний кеш вида

\[
StoreCache: Selector \rightarrow MemoizedSelector,
\]

то каждому селектору сопоставляется его мемоизированная версия, а уже внутри этой версии применяется слабое отображение по ключу `state`. Именно такая схема используется в `kiks`: `Store` хранит `WeakMap<Selector, MemoizedSelector>`, а мемоизированный селектор опирается на ссылочную идентичность состояния.

### 1.4.3. Сложность, память и сборщик мусора

Временная сложность:

- первый вызов: `O(k)`;
- повторный вызов для того же объекта состояния: `O(1)`.

Потребление памяти:

\[
M = O(1)
\]

на один живой объект состояния в типовом случае «один актуальный snapshot — один результат». Даже если записей несколько, память ограничивается количеством действительно достижимых ключей.

Поведение сборщика мусора является основным преимуществом данного варианта. Поскольку `WeakMap` не удерживает ключ сильной ссылкой, запись автоматически становится доступной для удаления, когда соответствующий объект состояния больше не достижим из программы [8], [9]. Это означает, что кеш не формирует неограниченно растущую структуру хранения и хорошо согласуется с долгоживущим приложением.

### 1.4.4. Преимущества и недостатки

Преимущества:

- константная стоимость повторного вызова;
- отсутствие необходимости вручную управлять размером кеша;
- корректное взаимодействие со сборщиком мусора;
- простая интеграция в `Store` и в React-подписки;
- хорошая стабилизация ссылок на производные данные.

Недостатки:

- кеш эффективен только при сохранении ссылочной идентичности состояния;
- не хранит несколько независимых наборов аргументов так же явно, как LRU;
- требует объектного представления состояния, а не примитивного ключа.

### 1.4.5. Пример реального использования

Этот вариант соответствует текущей реализации `kiks`. Выбор такого подхода согласуется с целями проекта: минимальный размер библиотеки, отсутствие внешних зависимостей, работа через `useSyncExternalStore`, а также безопасное поведение по памяти.

**Вывод по подразделу 1.4.**  
WeakMap-мемоизация сочетает две критически важные характеристики: `O(1)` на повторном вызове и безопасную работу со сборщиком мусора. По совокупности архитектурных свойств этот вариант выглядит наиболее естественным кандидатом для ядра `kiks`.

## 1.5. Вариант 4. Мемоизация с зависимостями (`input selectors`)

### 1.5.1. Определение и математическая основа

В этом варианте итоговый селектор строится как композиция функций:

\[
g(x) = f(s_1(x), s_2(x), \dots, s_n(x)),
\]

где `s_1, s_2, ..., s_n` — входные селекторы, извлекающие отдельные зависимости из состояния, а `f` — проектор, вычисляющий итоговое производное значение.

Пересчёт выполняется только тогда, когда хотя бы одна зависимость изменилась:

\[
\exists i \in \{1,\dots,n\}: s_i(x_{curr}) \neq s_i(x_{prev}).
\]

Если все входные селекторы возвращают те же значения, проектор `f` не запускается повторно.

### 1.5.2. Алгоритм работы

Псевдокод:

```text
function select(state):
    deps = [s1(state), s2(state), ..., sn(state)]
    if deps == previousDeps:
        return previousResult
    result = f(deps)
    previousDeps = deps
    previousResult = result
    return result
```

С математической точки зрения данный подход оптимизирует не весь объект состояния, а только вектор зависимостей

\[
\mathbf{d}(x) = (s_1(x), s_2(x), \dots, s_n(x)).
\]

### 1.5.3. Сложность, память и сборщик мусора

Временная сложность:

- первый вызов:

\[
T_{\text{first}} = O\!\left(\sum_{i=1}^{n} c_i + k\right),
\]

где `c_i` — стоимость вычисления `s_i(x)`, а `k` — стоимость проектора;

- повторный вызов:

\[
T_{\text{repeat}} = O(n)
\]

на сравнение зависимостей и `O(1)` на возврат результата после успешной проверки.

Потребление памяти:

\[
M = O(n),
\]

так как необходимо хранить вектор последних зависимостей и последний результат.

Поведение сборщика мусора в целом корректно, но менее «естественное», чем у `WeakMap`. Зависимости и результат удерживаются сильными ссылками в замыкании до тех пор, пока жив сам селектор. Утечка как неограниченный рост структуры не возникает, однако последний набор зависимостей сохраняется дольше, чем при слабом отображении.

### 1.5.4. Преимущества и недостатки

Преимущества:

- высокая точность мемоизации: проверяется только значимая часть состояния;
- удобство для сложных составных селекторов;
- хорошая совместимость с композиционным стилем проектирования.

Недостатки:

- большее число сравнений на повторном вызове;
- дополнительная сложность API и реализации;
- необходимость проектировать и поддерживать входные селекторы;
- менее прозрачная интеграция в минималистичное ядро.

### 1.5.5. Пример реального использования

Данный подход характерен для архитектуры `Reselect` и `Redux Toolkit`, где итоговый селектор строится через явный список `input selectors`, а затем — через проектор [3], [4]. Важно подчеркнуть, что в реальных версиях `Reselect v5` внутренняя реализация мемоизации может использовать разные мемоизаторы, однако сама модель декомпозиции на входные селекторы соответствует именно рассматриваемому четвертому варианту.

**Вывод по подразделу 1.5.**  
Мемоизация по зависимостям обеспечивает гибкое и выразительное решение для сложных вычислений, однако её цена — дополнительная логика сравнения и более сложная интеграция. Для минималистичной библиотеки этот вариант силён концептуально, но не обязательно оптимален как базовый механизм ядра.

## 1.6. Сравнительный вывод по четырём вариантам мемоизации

Проведённый анализ показывает, что все четыре варианта представляют разные инженерные компромиссы.

1. Baseline-подход выигрывает в простоте, но полностью проигрывает в повторных вычислениях.
2. LRU-кеш хорошо работает при повторяющихся запросах, но создаёт дополнительную инфраструктуру и сильные ссылки.
3. WeakMap-мемоизация обеспечивает константную стоимость повторного вызова и безопасное управление памятью.
4. Мемоизация с зависимостями даёт более точный контроль над пересчётом, но увеличивает сложность интерфейса и стоимость повторного вызова за счёт проверки входных селекторов.

Следовательно, дальнейшее сравнение должно быть выполнено уже не качественно, а формально — с помощью методов многокритериального выбора.

**Вывод по разделу 1.**  
С точки зрения теории алгоритмов и архитектуры библиотек управления состоянием вариант с `WeakMap` является сильнейшим кандидатом, однако для научной обоснованности этого недостаточно. Необходимо формально доказать его преимущество в рамках единой процедуры многокритериального выбора.

# 2. Формальные методы выбора лучшей реализации мемоизации

## 2.1. Критерии и исходная матрица альтернатив

Для дальнейшего выбора используются четыре альтернативы:

- `A1` — отсутствие мемоизации;
- `A2` — LRU-кэш;
- `A3` — WeakMap-мемоизация;
- `A4` — мемоизация по зависимостям.

Сравнение выполняется по шести критериям:

- `C1` — время первого вычисления (меньше — лучше);
- `C2` — время повторного вычисления (меньше — лучше);
- `C3` — потребление памяти (меньше — лучше);
- `C4` — сложность реализации (меньше — лучше);
- `C5` — безопасность памяти / отсутствие утечек (больше — лучше);
- `C6` — удобство интеграции в `Store` (больше — лучше).

## 2.2. Метод Парето

Метод Парето применяется как предварительный фильтр. Альтернатива `A_i` считается доминируемой альтернативой `A_j`, если `A_j` не хуже `A_i` по всем критериям и строго лучше хотя бы по одному.

Формально:

\[
A_j \succ A_i \Leftrightarrow
\begin{cases}
a_{jk} \le a_{ik}, & \text{для стоимостных критериев}\\
a_{jk} \ge a_{ik}, & \text{для критериев полезности}
\end{cases}
\]

и хотя бы одно неравенство строгое.

Сравнение показывает следующее.

1. `A2` доминируется `A3`, поскольку `A3` не хуже `A2` по `C1` и `C2`, лучше по `C3`, `C4`, `C5`, `C6`.
2. `A4` доминируется `A3`, поскольку `A3` лучше по всем шести критериям.
3. `A1` не доминируется `A3`, так как выигрывает у него по `C1`, `C3`, `C4`.

Следовательно, множество Парето имеет вид:

\[
P = \{A1, A3\}.
\]

**Таблица 2.2 — Результат фильтрации по Парето**

| Альтернатива | Статус |
|---|---|
| `A1` Без мемоизации | входит в множество Парето |
| `A2` LRU-кэш | исключается, доминируется `A3` |
| `A3` WeakMap | входит в множество Парето |
| `A4` Input selectors | исключается, доминируется `A3` |

**Вывод по подразделу 2.2.**  
Метод Парето сразу сокращает множество альтернатив до двух принципиально сильных кандидатов: `A1` и `A3`. Это уже показывает, что WeakMap-подход не только конкурентоспособен, но и доминирует более сложные варианты LRU и input selectors в выбранной постановке задачи.

## 2.3. Метод анализа иерархий (AHP)

### 2.3.1. Матрица попарных сравнений критериев

На следующем шаге необходимо определить веса критериев. Используется метод анализа иерархий Т. Саати [10], [11]. В качестве экспертной модели примем следующую логику:

- повторное вычисление (`C2`) важнее первого (`C1`), поскольку селекторы в интерфейсе вызываются многократно;
- безопасность памяти (`C5`) и удобство интеграции (`C6`) столь же значимы, как скорость повторного вызова;
- потребление памяти (`C3`) важнее первого вызова, но уступает `C2`, `C5`, `C6`;
- сложность реализации (`C4`) важна, но не должна перевешивать runtime-свойства.

Для согласованного набора экспертных предпочтений используется вектор относительной важности:

\[
v = (1, 3, 2, 1, 3, 3).
\]

Тогда матрица попарных сравнений задаётся отношением

\[
a_{ij} = \frac{v_i}{v_j}.
\]

### 2.3.3. Проверка согласованности

Для матрицы, построенной на строго согласованном векторе отношений, выполняется:

\[

Тогда индекс согласованности:

## 2.4. Метод взвешенной суммы (WSM)

Метод взвешенной суммы использует формулу

\[

\]

где `w_i` — веса критериев из AHP, `x_ij` — нормализованная оценка альтернативы `j` по критерию `i`.

Для стоимостных критериев используется нормализация:

\[
x_{ij} = \frac{\min a_i}{a_{ij}}.
\]

Для критериев полезности:

\[
x_{ij} = \frac{a_{ij}}{\max a_i}.
\]

## 2.5. Метод TOPSIS

Метод TOPSIS предполагает, что лучшая альтернатива должна находиться как можно ближе к идеальному решению `A+` и как можно дальше от антиидеального решения `A−` [12], [15].

### 2.5.1. Нормализация и взвешенная матрица

Для каждого критерия выполняется векторная нормализация:

\[
r_{ij} = \frac{a_{ij}}{\sqrt{\sum_{j=1}^{m} a_{ij}^2}}.
\]

Затем:

\[
v_{ij} = w_i \cdot r_{ij}.
\]

| `A3` | 0.0363 | 0.0492 | 0.0562 | 0.0227 | 0.1477 | 0.1570 |
| `A4` | 0.0544 | 0.0984 | 0.0843 | 0.0567 | 0.1182 | 0.0942 |

### 2.5.2. Идеальная и антиидеальная альтернативы

С учётом направленности критериев получаем:

\[

\]

\[
A^- = (0{,}0544,\ 0{,}1968,\ 0{,}1124,\ 0{,}0567,\ 0{,}0591,\ 0{,}0628).
\]

### 2.5.3. Расстояния и коэффициент близости

Расстояние до идеального и антиидеального решения вычисляется по формулам:

\[
D_j^+ = \sqrt{\sum_{i=1}^{m}(v_{ij} - v_i^+)^2},
\]

\[
D_j^- = \sqrt{\sum_{i=1}^{m}(v_{ij} - v_i^-)^2}.
\]

Коэффициент близости:

\[
C_j = \frac{D_j^-}{D_j^+ + D_j^-}.
\]

Метод TOPSIS подтверждает предыдущий результат: WeakMap-мемоизация находится одновременно ближе всего к идеальной альтернативе и дальше всего от худшей. Это особенно важно, поскольку TOPSIS учитывает не только суммарный вес критериев, но и геометрическое положение альтернатив в многомерном пространстве решений.

# 3. Итоговый выбор и связь с `kiks` и конкурентными библиотеками

## 3.1. Почему побеждает WeakMap-мемоизация

Итоговый результат исследования можно сформулировать следующим образом: при сравнении четырёх вариантов мемоизации селекторов и применении четырёх методов многокритериального выбора победителем оказывается WeakMap-мемоизация (`A3`).

Причины этого выбора состоят в следующем.

1. **Константная стоимость повторного вызова.**  
   Если объект состояния не изменился по ссылке, результат возвращается за `O(1)`.

2. **Отсутствие риска неконтролируемого удержания данных.**  
   `WeakMap` не препятствует удалению ключей сборщиком мусора, когда соответствующие объекты состояния становятся недостижимыми.

3. **Простая интеграция в ядро `Store`.**  
   Для `kiks` такой подход естественно реализуется через `WeakMap<Selector, MemoizedSelector>`, не требуя внешних зависимостей и сложной управляющей логики.

4. **Совместимость с React-интеграцией.**  
   Стабильность производных ссылок хорошо сочетается с `useSyncExternalStore`, поскольку уменьшает вероятность лишних пересчётов и упрощает reasoning о snapshot-значениях.

Следовательно, WeakMap-подход является не просто одним из возможных, а именно целевым архитектурным решением для `kiks`.

Победа WeakMap-мемоизации объясняется тем, что этот метод обеспечивает лучший баланс между скоростью повторного доступа, безопасностью памяти и архитектурной простотой. Именно такое сочетание критериев является определяющим для минималистичной библиотеки управления состоянием.
